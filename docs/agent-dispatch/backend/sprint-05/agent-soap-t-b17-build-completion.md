**How the engine works** (`engine.ts`, `JobsLive: Layer<Jobs, never, Db>`):
- **Enqueue** runs in the caller's `Tx`. It does `insert … on conflict (key) where state in ('queued','claimed') do nothing returning id`, so a live key never aborts the caller's transaction. If nothing was inserted, it reads the live job and returns it with `created: false`. If that job finished between the two statements, it inserts again. `run_after` comes from Clock, and `{ partition }` sets `partition_key`.
- **Claim** is one transaction. It selects the oldest due queued job of the worker's kinds whose partition has no claimed job, using `FOR UPDATE SKIP LOCKED`. It then raises `claim_no` and `attempts` and sets `claimed_by` and `claim_expires_at` to Clock + 30 s.
  - If `jobs_one_claimed_per_partition_uq` refuses the update, `Db.withTransaction` returns it as `AlreadyExists` naming that constraint. The claim treats it as a skip: the transaction rolls back, so no attempt and no claim number are spent, and the claim looks again.
  - Any other rule broken there is a defect.
- **Runs:** a worker runs one job at a time and polls every 1 s (`Schedule.spaced`). A check-in fiber pushes the expiry out every 10 s, and the reaper runs every 10 s.
- **Finish** is one transaction. It marks the job done, fenced on `id`, the current `claim_no` and `state = 'claimed'`, then runs the save and ends with `Db.commitWithEvents`, so a save may append events.
  - No matching row means `ClaimLost`, and the save rolls back.
  - A save that breaks a database rule is a defect, so the job fails and retries.
- **When apply ends:**
  - It returns without finishing: the worker finishes the job with no save.
  - It fails with `ClaimLost`: the failure is dropped.
  - Any other failure or defect: `fail`, fenced on `claim_no`. The job goes back to queued with `run_after` = Clock + 10 s, 30 s, 2 min or 10 min, or is dead after the 5th failure. `last_error` gets the error's message.
- **Kill** interrupts the claim loop, the reaper and the check-ins. It leaves the run in flight alone, so a later save from it goes through finish and is refused.
- **Stop** does the same as kill, then interrupts the run and hands its claim back (fenced) so another worker can take it at once.
- **startConsumer**, only as far as T-B13-10 needs (E8):
  - It makes the cursor row if it's missing.
  - Each 1 s poll reads the events after `last_seq`.
  - For each event, in one transaction: a compare-and-swap moves `last_seq` from the seq it read to the event's seq. Only a copy that won the swap runs `handle`.
  - So two copies never both act. A handler that fails rolls the swap back, and the event is tried again on the next poll. The log line gives only the consumer's name and the seq.
  - The claim number, the backoff and handler writes through `Tx` are T-B18's.

## Deviations

- **The backoff is a table of `Duration`s, not a `Schedule`.** The lead's note says "every timing is a Schedule". The poll, the check-in and the reaper are Schedules. The backoff isn't an in-process wait: it's a `run_after` written to the row, from Clock, so it survives a restart, and TestClock drives it all the same (T-B13-06 checks each gap to the second). A Schedule would need stepping by hand to read the nth delay.
- **The 0004 snapshot keeps 0003's `missions_name_ck`.** drizzle-kit also wanted to drop and re-add `missions_name_ck`, because `factory.ts` says `(length(btrim(name)) > 0)` while migration 0003, the database and the db suite's change list say `(name <> ''::text)`. That drift is older than this ticket and isn't CR-44's, so I took those two statements out of 0004 and kept 0003's value in the 0004 snapshot. The drift stays visible to the next `generate`. See Limitations.
- **Interface:** unchanged. `jobs.ts` is byte-identical to `330b6ec`.

## Limitations

- **The dispute above:** `pnpm --filter @avel/db test`, `pnpm test` and the last verification line stay red on `done-when-2.count.test.ts` until its count reads 89.
- **Found, not in this ticket (out-of-scope note for Axis):** `packages/db/src/schema/factory.ts:572` defines `missions_name_ck` as `(length(btrim(name)) > 0)`, but the applied migration (0003) and `changes.ts` (CR-W22) have `(name <> ''::text)`. The tests pass because done-when 8 reads the live database. Any future `drizzle-kit generate` will try to rewrite the check until someone decides which form is meant.
- **A worker runs one job at a time.** No test or doc asks for more, and the design gives no number.
- **Attempts:** a stop's hand-back and the reaper's requeue don't refund the attempt the claim counted. `attempts` counts runs started, as the interface says.
- **Consumers:** the copy that wins the swap holds the cursor row's lock while `handle` runs. The other copy's swap waits, then finds the cursor moved. A crash mid-handle therefore holds the row until the connection dies, and the kill semantics for consumers are T-B18's.
- **Starting workers in the running server:** not done. Step 1 has no job kind yet (plan note, E8).
